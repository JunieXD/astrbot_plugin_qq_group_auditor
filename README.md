# astrbot_plugin_qq_group_auditor

`astrbot_plugin_qq_group_auditor` 是 AstrBot 插件，用于 QQ 群加群申请审核。插件在收到加群申请时，会调用当前 AstrBot LLM/provider 判断申请答案是否符合群规则，并根据每个群的配置自动通过、忽略或拒绝。

## 适用场景

- 支持 QQ OneBot v11 / aiocqhttp / NapCat 适配器。
- Bot 必须是群管理员，否则 OneBot 审核接口会失败，插件无法完成自动通过或拒绝。
- 适合需要按申请答案自动初筛加群请求，并把异常情况通知管理员的 QQ 群。

## WebUI 配置

安装插件后，在 AstrBot WebUI 的插件配置中编辑 `group_audits`。该字段使用 `template_list`，可以为多个群分别添加独立配置。

每个群可配置：

| 字段 | 说明 |
| --- | --- |
| `enabled` | 是否启用此群审核。 |
| `group_id` | QQ 群号。 |
| `review_prompt` | 审核提示词，用来描述什么样的申请答案可以通过。 |
| `failure_action` | 不通过动作，只能填写 `ignore` 或 `reject`。 |
| `invite_action` | 受邀入群动作，可填写 `approve`、`ignore` 或 `reject`，默认 `ignore`。 |
| `reject_reason` | 固定拒绝理由，在 `failure_action=reject` 或 `invite_action=reject` 时用于平台拒绝消息。 |
| `admin_qq_ids` | 管理员 QQ 号列表，用于接收异常通知，也用于私聊测试命令权限校验。 |
| `notify_on_approve` | 正常自动通过时是否通知管理员。 |
| `notify_on_reject` | 正常自动拒绝时是否通知管理员。 |
| `notify_on_ignore` | 正常忽略时是否通知管理员。 |
| `audit_log_enabled` | 是否保存每次申请、审批、入群和退群记录，默认开启。 |
| `auto_set_card` | 新成员实际入群后是否自动修改群名片，默认关闭。 |
| `card_template` | 群名片模板，默认 `{nickname}`。 |
| `application_question` | 平台无法读取加群问题时使用的备用问题文本。 |

## 入群审计记录

插件使用 SQLite 为每一次申请保存独立记录。同一个 QQ 退群、被踢或重新申请时不会覆盖旧记录。审计内容包括：

- QQ号、申请时间、申请时昵称、问题快照、答案和原始验证信息。
- 插件审核决定、平台审批动作、操作者 QQ、执行结果和错误信息。
- 实际入群时间、批准或邀请人、主动退群或被踢时间及操作者。
- 群名片修改前后的内容和执行结果。

数据库位于 AstrBot 的 `data/plugin_data/astrbot_plugin_qq_group_auditor/audit.sqlite3`，默认长期保留。

管理员可以私聊 Bot 查询：

```text
/qgaudit history <群号> <QQ号> [条数]
/qgaudit detail <群号> <记录ID>
```

没有对应申请的直接邀请入群会使用 `J<编号>` 作为记录ID，同样可以传给 `detail` 查询。

只有该群 `admin_qq_ids` 中的 QQ 可以查询。申请答案可能包含个人信息，不支持在群聊中查询。

NapCat 当前群系统消息接口只能说明申请是否已处理以及操作者，不能区分其他管理员执行的拒绝和忽略。插件按照统一规则，将“已处理但未观察到实际入群”的外部操作记录为 `reject`，并标记来源为 `external_inferred`。

受邀入群请求会保存为独立的 `invite` 类型申请，策略处理流水来源标记为 `invite_policy`。即使 `auto_set_card` 已开启，受邀成员也不会被实时补偿、定时补偿或 `/qgaudit backfill` 修改群名片。

插件启动、更新或重新启用后，会通过群系统消息同步补审停机期间遗漏且平台仍明确标记为“未处理”的申请。已经被任何管理员处理、已有插件处理结果或所属群当前停用的记录不会补审；实时事件与补审使用同一申请锁，避免重复调用 LLM 或审批接口。同步先保存整批请求及处理状态，再补审仍有效的申请，每轮最多补审 10 条。实际审批遵循 `automation_pacing` 中的审核等待与账号操作间隔，单条异常不会中断其他申请。补审产生的流水来源标记为 `plugin_catch_up`。NapCat 当前不会返回需要管理员确认的成员邀请，因此这类邀请主要依赖实时事件。

普通申请列表兼容 NapCat 用 `invitor_uin` 返回申请人 QQ 的格式，以及其他适配器的 `requester_uin` / `user_id` 字段。等待审批时被重载中断的申请，在平台仍显示未处理且没有已完成或结果未知的审批操作时，可以继续补审；真正邀请事件中的邀请人字段不使用这一转换。缺少申请人 QQ 的系统记录会记录跳过原因。

后台同步默认每 600 秒加 0–300 秒随机等待执行一次，通过 `background_sync_interval_seconds` 调整（最少 300 秒）。同步前只读取 NapCat 的本地在线状态；掉线、断开连接或接口失败后延长重试间隔，默认最长 1 小时，不再每分钟请求 QQ 或反复打印异常堆栈。历史查询共用同步间隔和锁，不会触发额外并发轮询；只从当前适配器发现平台，不再使用数据库里过期的平台 ID 轮询。`background_sync_enabled=false` 可关闭后台申请同步和定时名片补处理，实时审核、空答案等待及实时入退群处理继续生效。

## 审核专用模型与 ECNU 设置

在插件配置的 `llm_review` 中设置，仅影响本插件的实时审核、补审和 `/qgaudit test`：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `provider_id` | 空 | 指定 AstrBot 模型 ID，例如 `ecnu/ecnu-plus`；留空继承当前会话或默认模型。 |
| `ecnu_structured_output` | `true` | 对 ECNU Plus / Max 使用 JSON Schema，固定 `approve` 布尔值及 `reason` 字符串，禁止额外字段。关闭时审核请求不传 `response_format`。 |
| `ecnu_thinking` | `inherit` | `inherit` 继承共享模型设置；`enabled` 开启；`disabled` 关闭。 |
| `ecnu_reasoning_effort` | `low` | 仅在本插件设置 `enabled` 时覆盖档位。Plus 支持 `low/medium/xhigh`，Max 支持 `low/high/max`。 |

推荐 ECNU Plus 开启 `low` 思考和 JSON Schema。配置适用于本插件管理的所有群，但各群仍使用自己的审核提示词。学校群可参考 [非985非211提示词](docs/prompts/non985-non211.txt) 或 [四非提示词](docs/prompts/four-non.txt)，按实际入群政策选择。四非示例采用 2022 年第二轮双一流 147 校名单（含985、211），允许可靠识别的简称；参考表修正 SDUT、SDUST、HBUT，不能识别或信息冲突时留人工。其他群无需改动规则。非985非211示例允许非985非211的双一流高校；“待确认”输出为 `approve=false`，随后遵循该群 `failure_action`，不是独立人工审核队列。

部分 AstrBot 4.x 版本会丢弃 `llm_generate` 的生成参数。插件为 ECNU 的 OpenAI Chat Completion 适配器创建请求专用副本，通过 `custom_extra_body` 传入参数；SDK 配置也独立复制，连接池仍归原 Provider 管理。保留其他模型配置、认证、代理、超时、重试和原始用量。不会临时改写共享 Provider、修改全局模型配置或给其他插件强加 JSON 输出。已有共享模型里的思考配置依然作用于其他调用；如需其他调用默认关闭，应另行移除共享配置中的思考覆盖项。

不支持的适配器、错误的思考档位会产生审核异常，不会默默降级或自动通过。Schema 只约束格式，不保证审核结论正确；保留 JSON 校验和重试一次的兜底。返回截断、内容过滤、工具调用或拒答标记时，即使正文恰好是合法 JSON，也按无效审核输出处理并保留原始用量。插件不额外压低输出 token 上限，避免截断思考和最终 JSON。所有审核入口共用最多 3 个模型调用并发槽，等待槽位不计入模型耗时；其他插件的调用不在这个限额内。

文档：[ECNU 结构化输出](https://developer.ecnu.edu.cn/vitepress/llm/api/structuredoutput.html)、[思考模式](https://developer.ecnu.edu.cn/vitepress/llm/thinking.html)。

## LLM 调用统计与缓存

默认开启本插件的 LLM 调用统计，独立保存在 `data/plugin_data/astrbot_plugin_qq_group_auditor/llm_usage.sqlite3`。逐次记录调用时间、申请记录 ID、群号、Provider、实际模型、来源（实时审核/补审/测试）、尝试序号、输入/输出/缓存命中/未命中/思考 token、耗时和结果。开启此功能之前的历史调用无法补回用量。

一次审核返回无效 JSON 后重试，会留下两条调用记录；即使最终申请被其他人处理，已经发生的模型消耗仍会保留。邀请策略、空答案等待和去重跳过没有调用 LLM 时不增加调用数。申请的 `/qgaudit detail` 结果中可查看关联调用及累计已知估算费用。

管理员私聊命令：

```text
/qgaudit stats
/qgaudit stats 30d
/qgaudit stats 7d 123456789
/qgaudit stats 7d all deepseek-v4-flash
/qgaudit export 30d 123456789
```

格式为 `/qgaudit stats|export [天数或7d] [群号|all] [模型名]`，默认最近 7 天，范围 1–3650 天，模型名精确匹配。`all` 仅包含操作者在 `admin_qq_ids` 中的群，停用群的已有记录也可查询。统计包含总调用数、有效/无效输出、失败/取消次数、插件重试次数、token 已知数量、加权缓存命中率、平均/P95 调用耗时及按币种汇总的费用。单次查询最多 10 万条，超过时须缩小范围，不会悄悄截断统计。

CSV 通过私聊文件返回，保存每条调用的完整指标、价格快照、提示词哈希、用量来源和可用的响应 ID，含 UTC 时间列；缺失数据用空单元格表示。如果已启用正文记录，也包含已保存的正文及截断标记。以公式符号开头的文本会加单引号，防止电子表格把模型输出当作公式。导出文件保存在插件数据目录的 `llm_exports`，再次导出时清理超过 24 小时的旧导出文件。

WebUI 插件配置中的“LLM 调用统计与成本估算”（`llm_statistics`）：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `enabled` | `true` | 记录本插件的模型调用；关闭后仍可查询保留的历史记录。 |
| `store_content` | `false` | 保存实际传入的系统提示词、用户提示词及最终输出，不保存思考正文。 |
| `store_response` | `false` | 单独保存最终输出 JSON，无需同时保存输入。与 `store_content` 任一个开启即保存输出；关闭后不清除已有内容。 |
| `store_usage` | `true` | 保存精简的原始 usage JSON，仅含白名单 token 计数及其明细，区分缺失、null 和 0，不保存任意供应商字段或密钥。 |
| `content_max_chars` | `20000` | 每个正文字段的保存上限，范围 256–200000；截断不改变实际模型输入。 |
| `retention_days` | `90` | 明细保留天数，0 表示永久保留，最大 3650；启动、查询、新调用及后台维护时按小时清理。加群审计历史不受影响。 |
| `prices` | 空列表 | 按模型配置单价；未配置时费用为未知，用量与耗时仍然记录。 |

每条价格配置包含 `model`、可选的 `provider_id`、计费单位 `currency`（三位币种代码如 `CNY`、`USD`，或额度单位 `CREDITS`），以及 `cached_input_per_million`、`uncached_input_per_million`、`output_per_million` 三种每百万 token 单价。单价填十进制数；空白为未知，0 才表示免费。`match_model=response` 默认按返回的实际模型名匹配，无模型返回时使用配置中的模型名；`match_model=configured` 按调用开始时配置的模型名匹配，适用于 ECNU 等对外服务名与返回后端模型名不同的服务；指定 Provider 的配置优先于同名通用配置，重复匹配使用第一条。调用开始时冻结价格配置，结束时按模型及开始时间确定价格快照；调用途中或日后修改价格不会重算已开始调用和历史费用。支持按缓存命中输入、未命中输入、输出这三种类别计价的服务，不包括独立的缓存写入、固定请求费等其他计费项目。

费用计算为 `(命中输入 × 命中单价 + 未命中输入 × 未命中单价 + 输出 × 输出单价) / 1000000`。思考 token 通常已包含在输出总数中，作为明细展示，不重复相加。如果缺少缓存拆分，仅在两种输入单价相同时给出单点估算；输入、输出总量及单价完整时，另存全部输入命中至全部输入未命中的费用上下限，保留缓存未知，不伪造单点费用。不同币种分别汇总。未知用量、未知单价和无法计算的调用不会被算成免费，统计中会显示计价覆盖率。

ECNU 价格配置可使用 `currency=CREDITS`、`match_model=configured`、`schedule=ecnu_peak`。填写谷时每百万 token 单价：Plus 命中输入 20、未命中输入 100、输出 400；Max 分别为 60、300、1200。模型填 `ecnu-plus` / `ecnu-max`，Provider 填实际 ID。按请求开始时的北京时间，周一至周五 08:00（含）至 23:00（不含）使用两倍价格，其余时段原价；不按操作系统时区，也不特殊处理法定调休。`schedule=flat` 为默认固定价格。来源：[ECNU 额度与限制](https://developer.ecnu.edu.cn/vitepress/llm/limit.html)（2026-09-25 核对），上游调整时应同步更新配置。额度不是人民币，统计不是平台账单。

费用区间覆盖的调用已包含已知单点费用，不应将两者相加。旧调用没有原始 usage、正文或价格时不会回填猜测值；完整明细和原始 usage 可从 CSV 导出查看。

优先读取原始 OpenAI/DeepSeek 用量，包括 DeepSeek 的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`；对其他适配器可使用 AstrBot 的通用用量并标明来源。缓存命中率按“已知命中 token 总数 / 同批调用的已知输入 token 总数”加权计算，同时展示覆盖次数。耗时从插件发起模型调用到返回或异常为止，包含 AstrBot 内部网络重试等待，不含 QQ 审批随机延迟、排队和通知。插件自己的 JSON 重试逐次记录；AstrBot/SDK 内部的网络重试未必逐次暴露，异常和中断也可能没有用量，因此这里是成本估算，不能视为平台账单。

统计先保存进行中记录，再保存模型返回和解析结果。重载会取消尚未完成的模型调用并记为 `cancelled`；进程直接退出后留下的进行中记录在下次加载时记为 `interrupted`，其用量保持未知。数据库锁定、不可写等统计故障会限频记录日志，审核继续执行。

提示词按稳定程度排列：所有群共用固定系统角色、JSON 输出要求和示例；用户消息依次放群规则、群号、申请答案、申请人 QQ。同群不同申请尽量共享较长前缀，答案相同的申请还能共享答案部分。重试指令追加在原提示词末尾。申请字段以 JSON 字符串编码，真实内容保留并明确作为待审核数据。实际缓存是否命中仍取决于服务商的前缀匹配、最小长度和过期策略，首次调用或规则修改后可能未命中，以返回用量为准。

## 自动群名片

`auto_set_card` 默认关闭。开启后，插件在自动批准申请后会主动确认成员是否已经入群，并在短时重试后继续通过定时任务核对。实时成员入群通知仍会正常处理，但即使 NapCat 偶尔没有发送 `group_increase`，名片设置也不会只依赖该通知。其他管理员手工通过的申请会在群系统消息同步后按同样流程处理。

NapCat 的申请验证消息可能是 `问题：毕业年份\n答案：2028`。插件会把完整文本保存在 `raw_comment` 供审计，同时把纯答案 `2028` 保存并用于审核和 `{answer}`，避免把问题标签写进群名片。

`card_template` 支持以下占位符：

| 占位符 | 内容 |
| --- | --- |
| `{qq}` | 成员 QQ 号。 |
| `{nickname}` | 成员当前 QQ 昵称，获取失败时使用 QQ 号。 |
| `{question}` | 申请时保存的问题快照。 |
| `{answer}` | 本次申请答案。 |
| `{join_date}` | 北京时间入群日期。 |
| `{join_time}` | 北京时间完整入群时间。 |

示例：

```text
{nickname}-{answer}
```

如果模板引用的申请答案不存在，例如成员由管理员直接邀请入群，插件会跳过修改并记录错误，不会生成残缺名片或清空现有名片。答案内容会移除换行和控制空白，最终名片最多保留 60 个字符。

### 补处理历史群名片

开启该群的 `auto_set_card` 后，配置中的管理员可以私聊 Bot 执行：

```text
/qgaudit backfill <群号>
```

命令按每个 QQ 最新的有效通过记录逐个处理。等待后先读取该成员的最新状态，确认在群内且名片为空才调用设置接口。明确拒绝、只有已结束成员会话或没有通过证据的申请不会处理；存在尚未结束的成员会话时优先使用该会话关联的申请。只有读取确认成员存在后才会补记成员会话，因此已退群成员的失败尝试不会被误记为仍在群内。

已经有成功名片操作记录的成员不会重复处理，命令可安全重复执行。NapCat 明确返回“成员不存在”时会单独计入“当前不在群内”，不会作为自动修改名片故障通知管理员；权限不足等其他错误计入“其他设置失败”。优先使用成员接口返回的入群时间和昵称；缺失时使用申请快照、审批时间或 QQ 号。

每次真正修改群名片前默认随机等待 30 至 90 秒，批量补处理按成员串行执行。单个成员失败只会计入本次结果，不会中断后续成员；后台自动补偿对每次申请最多调用 5 次，次数持久化到数据库，重启插件也不会重新无限尝试。管理员以后主动再次执行 `backfill` 时，每个候选成员在该次命令中仍只尝试一次。

插件不会覆盖审计记录中已知的非空群名片，也不会重复修改已有成功操作记录的成员。由于当前 NapCat 版本的群成员信息和列表接口不可用，而 `set_group_card` 本身不会返回修改前名片，因此对于数据库中从未记录过名片的历史成员，插件无法在不调用故障接口的前提下可靠判断其当前是否已有名片；这类成员执行 `backfill` 前请先确认范围。升级 NapCat 前，插件不会主动调用这两个故障接口。

## 审核规则

插件只在 LLM 返回严格 JSON，且 `approve=true` 时自动通过申请。

LLM 输出格式必须是 JSON：

```json
{"approve": true, "reason": "符合条件"}
```

其中：

- `approve` 必须是布尔值。
- `reason` 必须是字符串。
- `approve=false`、JSON 解析失败、字段类型不正确，都不会自动通过。

### DeepSeek JSON Output

当前聊天 provider 来自 DeepSeek 官方 API 时，插件会按照 [DeepSeek JSON Output 文档](https://api-docs.deepseek.com/guides/json_mode) 传入：

```json
{"response_format": {"type": "json_object"}}
```

插件不额外设置输出 token 上限，遵循模型提供商及 AstrBot 的配置。

审核提示词同时包含 `json` 关键字和目标格式示例。若模型仍返回空内容、无效 JSON 或错误字段结构，插件会追加格式纠正指令并重试一次。完整包裹返回内容的 `json` Markdown 代码块也可以解析；任意解释文字与 JSON 混合的响应仍会拒绝解析。

每次无法解析的原始返回都会以转义形式写入 warning 日志，最多保留前 500 个字符，便于定位空响应、代码块或额外说明文字，同时避免超长模型输出刷满日志。

## 不通过动作

当申请答案未通过审核时，插件按该群的 `failure_action` 处理：

- `ignore`：不调用平台审核接口，留给管理员手动处理。
- `reject`：自动拒绝，并使用该群配置的固定 `reject_reason`。

出于安全和可控性考虑，插件不会把 LLM 返回的 `reason` 发给申请人。`reason` 只用于管理员理解审核结果或排查问题。

## 空答案处理

普通主动申请的答案为空时，插件先等待 30 秒，期间不调用 LLM、审批接口或发送忽略通知。同一平台、同一群、同一申请人在等待期间提交有答案的新请求后，立即审核新请求，旧空答案记录标记为 `superseded`（来源 `empty_answer_wait`），不再单独审批或通知。不同申请标识也会在这个等待窗口内关联；同一标识补充答案时，审计记录会更新为补充后的答案。

重复空答案事件不会延长最初的等待时间。30 秒后仍没有答案，则只对窗口内最后一条空答案请求按原有 `failure_action` 和通知设置处理。邀请策略保持不变。插件卸载或重载会取消尚未到期的等待任务。

所有申请和邀请都进行请求状态检查：同平台、同群、同一申请人的更新请求会替代尚未提交审批的旧请求，旧记录标记为 `superseded`。等待期间已被其他管理员处理、已观察到入群，或其他申请已通过的旧请求标记为 `handled`。模型返回后、审批延迟结束后，以及忽略通知发送前都会重新检查；已经发出的审批不会被取消。已知离群后的新申请仍可重新审核。

NapCat 明确返回 `No such request` 时，只能确认该 flag 已不可用，不能据此认定申请已通过。插件将它记为 `unavailable`（可能已合并、撤回或被处理），不再重试、发送平台异常通知或累计账号失败次数。上述终止记录保存在审计数据库中，重载仍然有效，可通过 `history` / `detail` 查询。网络超时、权限不足等其他异常仍按原有机制处理。

普通申请中有问题文本但答案为空时不会调用 LLM，等待结束后仍为空才按该群配置的 `failure_action` 处理，避免把无意义内容发送给模型。

## 受邀入群处理

`invite_action` 为每个群单独控制受邀入群请求：

- `approve`：直接通过，不调用 LLM，也不自动修改该成员的群名片。
- `ignore`：不调用平台审批接口，保留给管理员手动处理；这是默认值。
- `reject`：直接拒绝，不调用 LLM，拒绝消息使用 `reject_reason`。

三种动作分别复用 `notify_on_approve`、`notify_on_ignore`、`notify_on_reject` 决定是否私聊通知管理员。

NapCat 当前把“群成员邀请他人且需要管理员确认”的实时事件发送成普通 `sub_type=add`，不提供邀请者或请求类型字段，同时也不在 `get_group_system_msg` 中返回这类通知。插件因此仅在“原始申请附言完全为空”时将事件识别为受邀入群。`问题：年级\n答案：` 这类仍属于普通空答案；如果群允许主动申请时把整段验证信息留空，平台数据本身无法与受邀入群区分，也会按 `invite_action` 处理。

## 管理员通知

以下情况会私聊通知该群配置的管理员：

- LLM 调用异常。
- LLM 返回内容不是合法 JSON，或不符合 `approve` / `reason` 字段要求。
- OneBot 平台审核接口失败，例如 Bot 不是群管理员、网络超时或适配器返回未知错误；明确的 `No such request` 按上述请求失效流程记录。

正常通过、拒绝、忽略是否通知管理员，由 `notify_on_approve`、`notify_on_reject`、`notify_on_ignore` 控制。

## 私聊测试命令

群管理员可以私聊 Bot 测试某个群的审核提示词：

```text
/qgaudit test <群号> <申请答案>
```

示例：

```text
/qgaudit test 123456789 我已经阅读群规，会遵守讨论主题
```

命令会调用当前 LLM/provider，并返回类似结果：

```text
approve=True reason=符合条件
```

只有该群 `admin_qq_ids` 中的 QQ 可以使用测试命令。真实 AstrBot 命令解析可能剥离开头的 `/`，插件同时兼容 `qgaudit test ...`，但用户文档中仍推荐使用 `/qgaudit test ...`。

## 自动操作节奏

在插件配置的“自动操作节奏与冷却”（`automation_pacing`）中调整：

| 参数前缀 | 默认范围／值 | 用途 |
| --- | --- | --- |
| `review_min_seconds` / `review_max_seconds` | 5–15 秒 | 主动申请、邀请通过／拒绝和补审的全局默认等待 |
| `card_min_seconds` / `card_max_seconds` | 30–90 秒 | 名片操作等待，等待后检查真实名片 |
| `action_gap_min_seconds` / `action_gap_max_seconds` | 8–15 秒 | 同账号管理与通知操作间隔，通知设置不能缩短此间隔 |
| `notice_min_seconds` / `notice_max_seconds` | 10–20 秒 | 管理员通知等待和间隔 |
| `recovery_min_seconds` / `recovery_max_seconds` | 60–180 秒 | 检测到离线后的恢复等待 |
| `failure_threshold` / `failure_cooldown_seconds` | 3 次／3600 秒 | 连续失败暂停该账号自动操作 |
| `notice_dedup_seconds` | 600 秒 | 相同管理员通知去重窗口 |
| `lookup_cache_seconds` | 1800 秒 | 群问题和昵称缓存 |
| `sync_jitter_seconds` | 300 秒 | 后台同步间隔额外随机等待上限 |

本插件和新版 GitHub 订阅在同一 AstrBot 进程中共享账号锁与冷却；无须同时安装两个插件。状态在 `data/plugin_data/qq_automation_guard/state.json`，请勿通过删除该文件清除重试保护。参数非法时回退默认值；最大延迟小于最小时自动按最小值处理。

审批和名片操作执行前检查本地 QQ 在线状态，离线暂停；等待期间人工已处理申请或设置名片时，插件会跳过对应写入。数据库不可用则暂停自动审核。管理员通知在离线或冷却时只记录本地日志，不积攒离线通知集中补发。审批调用结果未知时保留待核对记录，不自动重复提交；管理员可在 QQ 中核对处理。

随机等待在账号锁外进行：例如名片任务正在等待 90 秒时，后来的审核可在自己的 5–15 秒等待到期后先执行。所有实际操作仍共用账号锁，并保留上次操作完成后的间隔；同时到期的任务仍需排队，因此配置的审核等待不是总耗时上限。账号恢复等待对所有任务共同生效，重载也会保留。取消未执行的长等待任务不会提前占用后续操作的时间。

入群通知、审批后补偿和历史补处理使用同一成员锁，并重新读取已完成的名片记录，避免同一成员重复排队、查询或设置名片。共享调度器支持原地升级，重载加群审核插件即可升级当前进程里的调度对象，同时保留 GitHub 订阅插件使用的锁、间隔和冷却状态。

多群管理时，各申请独立等待，只有等待到期的任务才参与调度。审批优先于群名片，群名片优先于通知；同优先级按群轮转，同群按入队顺序执行。低优先级任务到期后每等待 60 秒提升一级优先级，避免持续审批导致名片和通知一直等待。实际写操作始终串行，并保持账号操作间隔。

每条“群审核配置”中可设置 `review_min_seconds` / `review_max_seconds`，默认 `-1` 表示分别继承全局值。例如全局 5–15 秒，某群配置 20–40 秒后，该群的主动申请、邀请及补审都等待 20–40 秒；账号间隔仍与其他群共享。已有明确配置的全局等待范围保持不变。

运行日志记录“QQ 操作入队／等待／开始／暂缓或跳过”，包含群号、任务类型、随机等待、最早执行时间、实际累计等待和等待原因。最早执行时间仅指随机延迟到期时间，后续账号间隔、其他群轮转和恢复冷却仍可能延后执行。

随机间隔用于分散自动操作，不能保证避免平台风控。命令查询结果和手动测试回复仍及时返回。

## 审核阶段诊断

`/qgaudit detail <群号> <记录ID>` 在原有模型决定、插件操作、其他管理员处理与入群记录之外，显示最近 100 条审核阶段记录。记录包括模型并发排队、模型开始/返回/输出校验、审批入队、随机等待、账号间隔/恢复等待、在线检查、平台操作开始/结束及本次审核总耗时。各阶段时长可能包含子阶段，不能简单相加；总耗时从进入本次审核开始，不含收到事件之前的时间。结束为 `handled` / `deferred` / `interrupted` 等状态时不意味着已经调用 QQ 审批接口。

阶段明细存入 `audit.sqlite3` 的 `application_phases` 表，遵循原有群审计范围，详情查询沿用管理员权限。阶段记录与 LLM 统计失败均不会阻止正常审核。重载保留共享队列中的其他任务、账号冷却及结果未知保护，不为补日志额外发送消息或重复审批。日志显式使用 AstrBot logger，新增阶段日志不打印申请正文、请求 flag、认证信息或模型思考正文。旧申请不会补造阶段记录。
